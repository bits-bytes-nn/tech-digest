# 변경 이력

`docs/design.md`는 코드가 지금 어떻게 동작하는지를 설명합니다. 이 문서는 그 규칙들이 어떤
사고와 측정에서 나왔는지를 주제별로 모아 둔 기록입니다. 날짜는 원래 기록에 적혀 있던 실행일이나
측정일이고, 날짜가 없는 항목은 기록에 날짜가 남아 있지 않은 변경입니다. 같은 주제 안에서는
대체로 오래된 것부터 적었습니다.

### 요청 계층

- `_make_robust_request`가 브라우저 프로파일 3종을 차례로 시도하던 시절, 헤더를 세션에
  `headers.update`로 써 넣었더니 세 세트가 대안이 아니라 누적이 되었습니다. Chrome 세트(12개)가
  실패한 뒤 Safari 세트(5개)를 덮어쓰면 Chrome의 `Sec-Ch-Ua`와 `Sec-Ch-Ua-Platform:
  "Windows"`가 남은 채 macOS Safari `User-Agent`가 나갔습니다. 실제 브라우저에서 나올 수 없는
  지문이라, 첫 시도 이후의 모든 재시도가 첫 시도보다 성공 확률이 낮았습니다. 헤더를 요청마다
  넘기도록 고쳤습니다.
- **2026-10-10** 헤더 세트를 하나로 줄이고 도메인별로 성공한 세트를 기억하던 `HeaderCache`를
  지웠습니다. 90일치 Batch 로그에서 두 번째·세 번째 세트가 첫 세트가 놓친 요청을 살린 적이
  없었습니다.
- **2026-10-10** `Content-Type`에 charset이 없는 페이지를 `requests`가 ISO-8859-1로 디코딩해,
  deepmind.google과 sebastianraschka.com의 모든 글이 모델에 닿기 전에 깨지고 있었습니다
  ("Xiaomiâs"). 이제 바이트를 BeautifulSoup에 넘겨 `<meta charset>`을 따르게 합니다.
- **2026-10-10** `RssFetcher`가 `feedparser.parse(url)`로 직접 내려받던 것을 요청 계층으로
  바꿨습니다. 소켓 타임아웃이 없어서, 연결만 받아 두고 멈춘 피드 호스트가 당시 3시간이던 Batch
  타임아웃까지 잡을 붙잡았고 Batch는 그걸 다시 재시도했습니다. 바꾼 뒤 설정된 피드 16개 모두
  엔트리 수와 bozo 여부가 예전 방식과 같았습니다.
- **2026-10-10** `CONTENT_SELECTORS`와 `DATE_FORMATS`를 설정된 소스가 실제로 쓰는 것만 남기고
  줄였습니다(`article`, `main`과 네 가지 날짜 형식).
- SSRF 가드가 IP 리터럴만 막던 것을 호스트명 해석과 정수 IPv4 표기까지 검사하도록
  넓혔습니다.

### 본문 추출

- **2026-08-19** `_scrape_full_content`가 `CONTENT_SELECTORS`를 순서대로 훑어 처음 매칭된
  요소를 그대로 돌려줘서, 어떤 셀렉터든 걸리면 `<body>` 폴백에 닿을 수 없었습니다. Hugging
  Face 블로그의 `<article>`은 헤딩만 담은 래퍼라 가시 텍스트 82자를 돌려줬고, 같은 페이지의

  21건이 이 경로로 콘텐츠 게이트에 걸려 사라졌고, 필터에는 5건만 닿았습니다. 게이트 로그는 글
  탓으로 읽혔습니다. 가장 많은 텍스트를 담은 컨테이너를 고르고 `<body>`의 절반에 못 미치면
  `<body>`를 쓰도록 고쳤습니다. HF 래퍼는 0.4%였습니다.

  `scraping.min_content_length`(600자 게이트)와 혼동되기 쉬웠습니다.
  `FULL_SCRAPE_TEXT_THRESHOLD`로 바꿨습니다.
- `Post.images`는 한동안 아무도 읽지 않는 데이터였습니다. 지금은 요약 속 이미지의 출처 검증에

  비어 있지 않다"를 요약 성공 신호로 썼기 때문에, 요약 호출이 실패한 글이 원문 티저를 본문으로
  달고 발송되면서 동시에 제외 리포트에도 올라갔습니다.

### 날짜

- 날짜 구간이 실행 당일 23:59:59에 끝났습니다. 01:00 UTC에 도는 잡은 그날 이후 게시된 글을 볼
  수 없었고 다음 주 구간은 그 23:59:59부터 시작해서, 실행일 01:00 이후 게시된 글(일주일
  168시간 중 23시간)은 어느 호에도 들어가지 않았습니다. 발행일 0시에서 끝나는 반열린 구간으로
  바꿨습니다.
- 오프셋이 없는 ISO 날짜를 `astimezone`이 컨테이너 로컬 시간으로 읽어, `TZ=Asia/Seoul`인
  Batch에서 "2026-10-04"가 10-03 15:00 UTC가 되어 10-04에 시작하는 구간 밖으로 밀렸습니다.
- `entry_date_text`가 `published`만 읽어서, `<updated>`만 있는 정상 Atom 피드의 엔트리는 전부
  fail-closed 게이트에 걸려 보이지 않게 버려질 수 있었습니다. 당시 설정된 피드 19개의 엔트리
  2,815건을 실측하니 모두 `published`가 있어서 이 폴백으로 되찾은 글은 없었습니다. "add new
  sources here" 경로의 함정을 없앤 변경입니다.
- **2026-08-19** 인덱스 스크레이퍼의 `_find_date_near_element`가 여러 게시물을 담은 조상에
  정규식을 걸어 문서 순서상 첫 날짜를 잡았습니다. 날짜가 없는 게시물이 이웃의 날짜를 물려받아
  사이트가 준 적 없는 날짜로 주간 윈도우에 들어왔습니다. 각 단계에서 다른 게시물 링크를 제거한
  뒤 검색하도록 고쳤고, 세 스크레이퍼에 복붙돼 있던 로직을 베이스 클래스 하나로 합쳤습니다.
  실제 HTML로 확인한 결과는 anthropic 9건에 고유 날짜 8개, meta 3건에 3개, xai 49건에
  41개였고 어느 사이트도 수집 건수가 줄지 않았습니다. 이 코드는 2026-10-10 스크레이퍼와 함께
  지웠습니다.

## 크롤러 헬스

- `EMPTY`가 "블로그가 조용했다"와 "피드가 이전했거나 셀렉터가 깨졌다"를 같은 한 줄로 보였습니다.
  보통 한 실행에서 19개 소스 중 12개가 `EMPTY`라, 깨진 크롤러 하나가 그 목록에 묻혀 몇 주를 버틸
  수 있었습니다. 날짜 필터 이전의 후보 수(`candidates`)와 `likely_broken`을 더했습니다. 처음
  계획은 "연속 몇 주 `EMPTY`인지 세기"였지만, 실행 간 상태가 필요하고 결론도 조치 불가능한
  알림이라 접었습니다.
- **2026-10-10** 후보를 매칭된 링크나 엔트리 전부로 세던 것을 날짜를 읽은 항목만 세도록
  바꿨습니다. Google Research 스크레이퍼 사례(위)가 계기입니다.
- x.ai(때로는 ai.meta.com)가 AWS 송신 IP를 사실상 매 실행 거부해 크롤 헬스 알림이 매주 무조건
  울렸습니다. 항상 울리는 알람은 새로 깨진 소스를 숨기므로 `expected_flaky_urls`를 만들어 두
  트리거에서 제외했습니다. 2026-10-10 해당 스크레이퍼를 지우면서 목록을 비웠습니다.
- 크롤 헬스 트리거가 둘이 된 뒤에도 문서는 하나만 설명하고 있었습니다.

## 재시도와 배치 처리 (`utils.py`)

- `retry_with_backoff`가 조건 없이 모두 재시도해서, 설정 하나가 잘못되면 글 하나당 최대 5회·약
  330초를 기다렸습니다. 필터는 글마다 한 번씩 부르므로 빈 다이제스트 알림이 나가기까지 한 시간
  넘게 걸렸습니다. 재시도 가능한 오류만 재시도하도록 바꿨습니다.

  치렀습니다. 원인 체인을 `__context__`까지 따라가면 복구 경로 안의 버그가 파싱 오류의 판정을
  물려받아 재시도됐습니다.
- `BatchProcessor`가 한 항목만 실패해도 청크 전체를 다시 돌려 성공한 호출까지 비용을 두 번
  냈습니다(5개 중 1개 실패 시 호출 9회).
- 재시도 함수가 정적 메서드 하나만 담은 `RetryableBase` 클래스였고 `Greeter`는 그 메서드에 닿기

  기본값으로 두 벌이던 백오프 상수를 한 벌로 합쳤습니다.
- 쓰지 않던 async 변형, 호출자가 넘긴 적 없는 `run_config`, `measure_execution_time`의 코루틴
  분기를 지웠습니다.

  않았습니다. 복구 프롬프트가 `instructions` 변수를 요구해 `KeyError`가 났고, 복구 모델은 호출조차

- **2026-10-11** 그날 prod 실행에서 필터 호출 하나가 읽기 제한 300초를 기다린 뒤 botocore의

## 프롬프트 캐싱

- 처음 구조에서는 정적 루브릭이 human 템플릿의 `{post}` 뒤에 있어 캐시가 구조적으로
  불가능했습니다. `cache_split_marker`로 정적 부분을 system 프리픽스로 옮겼습니다.
- 이 문서는 한동안 "요약 프리픽스는 바이트 단위로 동일하므로 캐시가 확실히 붙고, 필터링은 1,024
  토큰 경계에 걸려 보장되지 않는다"고 적었는데 둘 다 반대였습니다. `TokenUsageLogger` 기록을
  집계한 결과입니다.

  | 단계 | 호출 | 캐시 읽기 | 캐시 쓰기 |
  | --- | --- | --- | --- |
  | 필터링 | 74 | 84,834 | 31,420 |
  | 요약 | 24 | 0 | 109,398 |

  요약은 `max_posts`(3)가 `max_concurrency`보다 작아 배치 전체가 한 파도라 모든 호출이 냉
  캐시에서 출발했고, 쓰기 할증만 냈습니다. 절약액은 회당 5,207 토큰 프리픽스 3개에 대한 25%
  할증, 발행 1회에 1센트 남짓이었습니다. 금액보다 주석과 문서가 측정으로 반박되는 주장을 하고
  있었다는 점이 고친 이유였고, `_cache_can_hit`을 설정에서 유도해 `max_posts`를 올리면 저절로
  다시 켜지게 했습니다.
- **2026-08-19** 필터링 11건이 3청크로 돌았고 첫 청크 5건은 cache read 0, 이후 6건은 전부 read
  1,571이었습니다. 프리픽스가 Bedrock 최소치(1,024)를 넘어 정상 동작했습니다. 로그의
  `cache_write`가 0인 것은 `ChatBedrockConverse`가 `cache_creation`을 보고하지 않기 때문입니다.

- **2026-10-10** 시도 타임아웃을 3시간에서 90분으로 줄였습니다(가장 긴 실행이 7분 미만). 시도
  타임아웃·시도 횟수·RUNNABLE 한도를 `constants.py`의 세 상수로 옮겨 스택과 대기 시간이 같은
  값에서 나오게 했습니다. 컴퓨트 환경을 `ECS_AL2023`으로 고정했습니다. Batch의 ECS 최적화
  Amazon Linux 2 AMI는 2026-06-30에 지원이 끝났습니다.
- 한 역할이 EC2 호스트와 컨테이너를 겸해서 모든 호스트가 Bedrock·SES·S3·SSM 권한을, 모든
  컨테이너가 ECS 에이전트 권한을 가졌습니다.
- S3 권한이 공용 버킷 전체에 열려 있어 다른 워크로드의 데이터까지 읽고 덮어쓸 수 있었습니다.
  접두사로 좁히고 쓰지 않는 `DeleteObject`를 뺐습니다. SES는 쓰지 않는 `ses:SendEmail`을 함께
  주고 있었습니다.
- 검증용 `cdk synth`를 로컬에서 돌리면 운영 시크릿을 조용히 다시 쓰고 있었습니다. 쓰기 전에
  읽어 값이 같으면 쓰지 않습니다.
- dev 스택 소유의 NAT 게이트웨이를 두 스테이지가 공유합니다. 2026년 9월 비용은 $42.86이었습니다.
- synth와 테스트가 모두 통과하는 상태에서 S3 권한을 버킷 전체로 넓히고, 애플리케이션 추론
  프로파일 ARN을 빼고, 종료 코드 1의 EXIT 규칙을 지우고, Spot 순서를 내리고, FAILED 규칙을 다른
  상태로 바꾸는 다섯 가지 변경을 한꺼번에 넣어도 아무것도 실패하지 않았습니다. 합성 템플릿을
  단언하는 `tests/test_infra_stack.py`가 이때 생겼습니다. 합성 결과의 기본 출력 위치는 실행마다
  새 시스템 임시 디렉터리여서 매번 약 160MB의 `app/` 사본이 남았습니다.

## 컨테이너와 의존성

- 베이스 이미지는 digest로 고정했지만 Python 의존성은 `>=` 범위뿐이어서 이미지 빌드마다 다시
  해석됐습니다. `requirements.lock`을 도입했습니다. CI가 락을 constraints로 쓰기 전에는 핵심
  패키지 12개가 이미지와 전부 달랐고 langchain은 1.2 대 1.3이었습니다.
- 코드가 임포트하지 않는 `langchain` 메타패키지를 지웠습니다. 앱 전체를 임포트한 뒤
  `sys.modules`에 `langchain`·`langgraph`가 하나도 없는 것을 확인했고, 메타패키지가 langgraph
  트리와 `ormsgpack`을 끌고 와서 락이 71개에서 65개로 줄었습니다. 재생성하면서 selenium의 전이
  의존성 `websockets`가 15.0.1에서 17.0.1로 올랐습니다.
- `pytz`는 `run_batch.py`의 한 줄 때문에 있었습니다. 표준 라이브러리의 `datetime.UTC`로 바꾸고
  `pytz`와 `types-pytz`를 지웠습니다(락 65 → 64). Batch 이미지가 쓰지도 않는 `git`을 설치하고
  있어서 뺐습니다.
- 이미지 빌드 컨텍스트에서 루트 `.dockerignore`가 적용되지 않는다는 것을 모른 채, `cd app && mypy
  .`가 남기는 154MB `.mypy_cache`가 Batch 이미지에 들어가고 있었습니다. 타입 검사마다 자산 해시가
  바뀌어 코드 변경 없는 배포도 이미지를 다시 빌드·푸시했습니다. 맨 이름 패턴은 `app/` 최상위에만
  맞아서 `src/__pycache__`도 들어가고 있었습니다.
- `aws-cdk-lib`를 하한 대신 `==`로 고정했습니다.
